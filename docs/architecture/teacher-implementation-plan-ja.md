# MorseRunner Teacher 実装計画

計画版: 0.1 / 作成日: 2026-09-22

対象仕様: [要求仕様書 0.3-draft](teacher-specification-ja.md)。現行コードの基準は `teacher` ブランチの `e19920f0e605c5e9a162090bc9c949b5b3eb0087`。仕様書等の未commit変更も計画入力として確認した。
本書は実装順序と受入条件を定める。新機能の実装・性能測定・commit・pushを実施した記録ではない。性能の提案値や未確定事項を、計画の作成によって合意済みへ変更しない。

進捗追記（2026-09-24）: **P1-A～Fをレビュー・修正し、P2-A～EのWindows向け機能を実装・試験**。[P1](../teacher-p1.md)と[P2](../teacher-p2.md)の使用方法・検証結果を参照。以下の作業表には当初の計画も残している。ユーザー指定により対応OSはWindowsのみとする。

## 1. 到達点と進め方

最初の到達点は、標準タイミングの欧文・和文を、短縮ファイル名・検証済みの正解ラベル付きで一括生成できる状態とする。この時点で最初の学習を開始できる。

```text
P0 現行試作（完了）
  → P1 標準タイミング・schema 0.2・短縮命名・検証器
  → P2 和文・速度多様性・バッチ → G2 最初の学習データを発行
       ├→ P3 受信劣化・混信・実コンテスト録音
       └→ P4a クリーン音声での学習・既存方式との比較
              P3 + P4a → P4b 劣化音・実録音での評価
                         → P5 Lazarus推論統合・2種類の表示
```

P3とP4aは依存がなくなった部分から進められるという設計上の関係であり、現時点で作業者やエージェントを追加する計画ではない。1実装担当を前提に、レビュー可能な小単位で順に進める。

- P1～P2の最優先事項は、正しい音声と正解の同期。大量生成は検証器に合格してから行う。
- 既存schema 0.1とlegacy音声は回帰の基準として維持する。
- 対応OSはWindows x64とする。Windows上で符号・時刻・ファイル操作・実行性能を検証する。
- 各段階で生成器の版・設定・試験結果・既知の制約を保存し、検証済みのデータだけ次段階へ渡す。

## 2. コードから確認した実装上の制約

| 確認箇所 | 現状 | 計画への反映 |
|---|---|---|
| `tools/export_sample.lpr` | CLI、WAV保存、ラベル収集、manifest作成が同じプログラム内。包絡線2本と全ラベルをメモリ保持 | 新生成器をコアとCLIに分け、ブロック生成・逐次保存へ移す |
| `VCL/MorseKey.pas` | 共有グローバルKeyer、文字表は`array[char]`、整数WPM、legacyの間隔計算 | 和文を既存char配列へ無理に入れず、新コアにトークン表と標準タイミングを設ける |
| `Station.pas` | `MsgText`を蓄積して再エンコードし、局のEnvelopeを更新 | 予定ラベルと実際に消費したサンプルを区別し、同じ区間を二重出力しない |
| `Contest.pas` | 局の混合、雑音、ミュート、フィルタ等を処理。初期呼出しでは通常と異なる長さを返す | ブロック番号から時刻を推測せず、実際に採用・保存したフレーム数で時計を進める |
| `Main.pas` | 2つのContest出力を`PutData`へ渡す | 初回の録音対応は選択された1受信系統のmonoとし、受信系統IDを記録する |
| `RndFunc.pas`等 | 複数箇所がグローバルRandomを利用 | Teacherでは局・効果ごとに乱数状態を所有し、UI操作や他局追加による結果変化を避ける |
| `tests/test_export.ps1` | pinned upstreamとの波形比較、境界入力、上書き・競合試験がある | 旧試験を保持し、新コアの独立試験を追加する |

既存の無関係なコード整理や、GUI全体の移植を先行条件にしない。正解記録用のファイル書込みコールバックを共有Keyerや音声処理経路へ直接接続しない。

## 4. P1 — 標準タイミングの単局欧文データ

| 作業ID | 依存 | 実装する内容 | 成果物・受入条件 |
|---|---|---|---|
| P1-A データ契約 | P0 | schema 0.2の型、必須/任意/null、全ID、正解時刻、ファイル一覧、状態遷移、CLI設定を固定。欧文限定の初期対応集合を明示 | JSON Schema等の機械可読定義とサンプル。未実装の効果等は無効/適用外と識別でき、必須ファイルの欠落を許さない |
| P1-B ID・命名 | P1-A | UUID v4、128ビット全体のBase32、role・6桁part、path検査、排他的作成 | 仕様のUUID既知例と往復一致、42/44文字、番号限界、パス・衝突の拒否。音声seedとUUID生成を分離 |
| P1-C 標準タイミング | P1-A | Int64全体時計、累積理想時刻からの丸め、1:3:7、論理key-down/upと波形整形の分離 | 独立に計算した既知の符号列と一致。各境界誤差1サンプル以内。5～60 WPMのlegacy回帰が維持される |
| P1-D 波形・保存 | P1-B、P1-C | 新コアでブロック生成、mono PCM16 WAV、全JSONL、60秒分割、SHA-256、完了manifest確定 | 途中の分割で位相・包絡線・サンプルが欠落しない。単一WAV相当と分割WAVの連結結果が一致。全体波形を保持しない |
| P1-E 検証・移行 | P1-D | 独立検証CLI、参照整合、ファイルサイズ・ハッシュ・時刻、異常終了、旧形式の識別/変換 | 改ざん・欠落・中断を確実に拒否。変換できない旧情報は作らず理由を保存し、legacyを標準と表示しない |
| P1-F 配布可能な試作 | P1-E | 新CLIの使い方、再現用設定、実行証拠、Windows性能基準値 | G1合格。標準欧文の小規模データを生成・独立検証・再読込できる |

P1-Aで定義する保存状態は `Preparing → Rendering → Finalizing → Complete` とし、失敗・中断は `Failed` / `Cancelled` へ移す。途中出力を残す場合も完了manifestを作らない。出力先や一時ファイルを含むパスの不備は可能な限りレンダリング前に検出する。

ハッシュの循環を避けるため、まず音声・JSONLを閉じて検証し、これらを対象とする`validation.json`を確定する。最後にそのレポートも含めてmanifestへハッシュを記録する。独立検証CLIは完成済みmanifestと全収録ファイルを照合し、検証のたびに元セッション内のレポートを書き換えない。

G1の試験には、既知の短点/長点/文字間/語間、非整数サンプル長、分割位置を跨ぐ符号、最終立下り、パディング、音声seedを変えない再実行、出力先競合、書込み失敗の注入を含める。単に生成器と同じ関数で期待値を計算する試験にしない。

## 5. P2 — 和文と学習用バッチ

| 作業ID | 依存 | 実装する内容 | 成果物・受入条件 |
|---|---|---|---|
| P2-A 符号表 | G1 | 公式資料の採用版を固定、欧文の対象拡充、和文の数字・記号・手続符号を含む表を実装 | 全エントリに出典・符号列・テスト。意味が違っても同じ音になる候補を、誤って一対一へ固定しない |
| P2-B トークン化 | P2-A | かな・濁点・半濁点、原文対応、複合符号、欧文/和文切替、未定義試験符号 | UTF-8バイト位置に依存しない対応表。未知文字の黙示削除なし。複合符号に文字間が入らない |
| P2-C 速度多様性 | P2-B | 小数WPM、間隔拡張、緩やかな変速、打鍵の揺らぎ、局別の版管理された乱数 | 各条件をメタデータと実イベントで照合。和文の文字/分と換算WPMを混同しない |
| P2-D バッチ | P2-C | 設定/コーパス読込、生成件数・時間、進捗・取消、セッション単位の完了/失敗管理 | 一部失敗で既存の完了結果を破壊しない。同一設定で音声とラベル内容を再現できる |
| P2-E データ発行 | P2-D | 欧文/和文・速度・音程・文面の配分、分割一覧、データ索引、試験集合の固定 | G2合格。生成→独立検証→データ分割→読込が一括再現可能 |

最初の配分案は、欧文/和文×5速度帯（5～9、10～19、20～29、30～39、40～60）×3音程領域（200～499、500～899、900～1200 Hz）の30セル。各セルに同程度のメッセージ数を用意し、音声時間・送信トークン数の偏りも報告する。範囲内の値も変化させ、代表値だけで構成しない。

最初に全符号を通す小規模スモークデータを発行し、次に学習/検証/試験のグループ分割を固定した試験学習用データを発行する。容量・学習時間・精度の推移を測定してから規模を増やす。窓の重複や同一原音の加工版を別集合へ分けない。

G2ではWindows x64でCLIビルド、UTF-8、Base32、時刻、ファイル操作、生成器RTF・メモリ・1時間分のオフライン生成を検証する。実時間入力の耐久性はP3-Eで別に判定する。

## 6. P3 — 劣化音と実コンテスト録音

| 作業ID | 依存 | 内容 | 完了条件 |
|---|---|---|---|
| P3-A 効果の土台 | G2 | 効果順序、設定SNRと実測SNR、SIR、遅延、クリップ、ミュートの記録形式を固定 | 効果なしがG2の波形と一致。単独効果の測定値を再現できる |
| P3-B 単局劣化 | P3-A | 雑音・帯域制限→QSB/ドリフト→インパルス/AGC/クリップの順で追加 | 各効果単独のGolden WAVと評価設定。未知のタイミング補正を勝手に適用しない |
| P3-C 複数局 | P3-B | 局別レンダリング、開始時刻、局別音声、混合、局別乱数、SIR | 各局の実送信イベントと全体時刻の対応。非線形処理前後を区別して検証 |
| P3-D 録音接続 | P3-C | Stationの実消費区間とContest最終音声の対応、選択受信系統、容量上限付きキュー、writer worker、GUI操作 | 再エンコードでラベルが重複せず、実際の保存フレームと一致。記録ON/OFFで音声経路に影響を与えない |
| P3-E 耐久・異常系 | P3-D | 1時間リアルタイム入力、停止/取消、ミュート、書込み遅延、容量不足、キュー超過 | G3合格。通常条件で欠落・超過0。異常時は未完成扱いで理由を記録 |

既存GUIにはすでに雑音・QSB等の処理があるが、Teacherからの設定・seed・観測位置・効果順序が制御できるかを確認してから再利用する。学習用コアへGUI全体の状態を持ち込まない。

録音接続前に`Contest.GetAudio → AlSoundOut1.PutData`以降のクリッピング、変換、バッファの扱いも調査し、保存音声の処理位置を明記する。音声デバイスから実測録音した信号と、デバイス投入前の生成信号を同じものとして記録しない。

ミュート・欠落区間には学習除外の根拠を保存する。単にSNRが低いだけの区間を「絶対に聞こえない」と断定しない。

## 7. P4 — 学習と比較評価

P4aはG2から開始する。DeepCW等の実装調査は、その前に入出力・ライセンス・再現条件の整理だけを進めることも可能だが、採用や性能順位を事前に断定しない。

1. **比較条件の固定**: 対象commit、ライセンス、対応言語、入力レート、窓長、因果性/look-ahead、ハードウェア、試験データとの重複可能性を一覧化する。
2. **評価器の作成**: 生の送信トークンCER、短長点誤り、境界F1と許容時間差、無音時の誤出力/分、コールサイン完全一致、RTF、表示までの遅延を実装する。
3. **ベースライン**: 従来DSP方式と、実行可能な既存モデルを同じ固定試験音声で評価する。和文非対応は対象外として別記する。
4. **最初のモデル**: 音声から短長点・境界を推定し、アプリ側の符号表で文字化する方式を学習する。文字直接出力は同じ分割と評価条件で比較する。
5. **P4bへ拡張**: G3の劣化音・混信を加え、条件別の弱点を確認する。独立した実録音と人手で確認した正解による試験を追加する。
6. **推論仕様を固定**: 前処理、モデルの入出力、ストリーミング状態、学習用/実行用依存、モデルハッシュを確定する。ONNXを候補として演算子対応と出力一致を検証する。

G4の成果物はモデル、学習設定、データ版と分割、評価コード、速度帯・言語・受信条件別のレポート。クリーンCER 1%以下等の仕様上の提案値は初回測定後に照合し、未達なら課題を記録する。雑音下の保証値や全局同時分離の達成を推定で記載しない。

## 8. P5 — Lazarusアプリへの統合

- 版管理されたC ABI等の境界を設計し、モデルload/start/process/flush/reset/stop、メモリ所有権、時刻、エラーを定める。実際のAPI名は選定ランタイムに合わせる。
- 初めにWAV再生入力、その後にライブ入力を接続し、同じ前処理・推論経路を使用する。
- UIは忠実な復号文、読みやすい文章、未確定箇所を表示する。反復折畳み・空白整形・複合符号解釈を個別に記録し、元の結果へ戻せるようにする。
- workerからUIを直接操作せず、推論・保存の遅延が音声入力を止めない構成にする。
- Windows x64で実行用ライブラリのロード、音声、ファイル、表示、終了処理を試験する。

G5の成果物はWindows配布物、モデル/ABI版、録音・再生での試験結果、CPU性能、既知の制約とする。

## 9. 作業の区切り・証拠・仕様への対応

P1-A～P1-Fを最初の6つの変更単位とする。各単位で必要なコード、対応する試験、説明を揃える。ソース変更後は既存試験と影響範囲の検証を実施し、結果を記録する。commit・pushは実行を依頼された時点の範囲で行う。

| 仕様の要求 | 担当する計画項目 |
|---|---|
| F01～F06 符号・原文・和文・複合符号・未知・反復 | P1-A/C、P2-A/B、P3-D |
| 速度・物理時刻・波形 | P1-C/D、P2-C |
| 短縮命名・ID・manifest・整合性・互換性 | P1-A/B/D/E |
| バッチ・再現性・中断・長時間 | P1-D/E、P2-D/E、P3-E |
| 受信劣化・混信・最終音声 | P3-A～E |
| 学習・独立評価・データ漏洩防止 | P2-E、P4 |
| 推論契約・2種類の表示・Windows統合 | P4、P5 |

各段階の記録にはsource commit/dirty状態、バイナリハッシュ、環境、実行コマンド、設定、結果、未実施項目を含める。実装済み・検証済み・配布可能を区別する。

## 10. 先に解消する設計事項とリスク

| 項目 | 解消時点 | 扱い |
|---|---|---|
| schema 0.2の厳密な定義、旧形式で復元不能な項目 | P1-A/E | 型と例を固定。過去の生成日時・ソースhash等を捏造しない |
| 標準モードの波形整形と最終立下り | P1-C | 論理時刻を優先し、音声端点の意味をテストで固定 |
| path制限とGUID実装のOS差 | P1-B、P2-E | OS境界へ集約し、環境ごとの実際のファイル操作で検証 |
| 和文の採用表・モード切替・濁点の数え方 | P2-A/B | 公式資料と送信トークン定義を固定してからラベルを大量生成 |
| 既存GUIの再エンコード・2系統・乱数依存 | P3-D | 実サンプルの消費と保存を追跡。必要箇所のみ変更 |
| 既存方式や推論ランタイムの採用可否 | P4 | 入出力、ライセンス、ビルド、速度・精度の実測で選ぶ |
| 実録音、基準PCの利用可否 | P2～P5 | 準備できる試験を先行し、未検証を明記。入手できないデータの成績を作らない |

現段階では暦日による納期を固定しない。P1-A～Cの実装量と試験時間を測定してP1残作業を見積もり、各ゲートで以後の計画を更新する。モデルの学習時間と実録音の正解作成は、生成器の実装時間と分けて見積もる。

## 11. 次に着手する具体的な作業

P1-A～FのレビューでBase32逆変換、JSONL読込上限、実行ファイル特定を補修した。P2-A～EはWindowsで実装し、schema 0.3の単一セッション・30セルの機能スモーク・独立検証まで確認した。小規模コーパスによるスモークはモデルの精度評価用集合ではない。次のP3では受信劣化と複数局へ進み、P4aのクリーン音声学習は独立の固定試験集合を準備して開始する。
